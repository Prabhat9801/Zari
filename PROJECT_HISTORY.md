# Zari — project history

A record of how this system got built, what broke in production, and why the
non-obvious decisions were made. Written for whoever — human or agent — opens
this repo next on a machine that has none of the context.

Read in this order: [CLAUDE.md](CLAUDE.md) for the current state,
[ZARI_SYSTEM_PROMPT.txt](ZARI_SYSTEM_PROMPT.txt) for the whole product spec,
[DEPLOYMENT.md](DEPLOYMENT.md) to deploy, and this file for the *why*.

**Keep this file current.** Every session that changes behaviour should add to
the log at the bottom. Git commit messages carry the detail; this file carries
the narrative and the traps, which is what saves the next person a day.

---

## How the project got here

**It started on Replit.** The original brief is [prompt.txt](prompt.txt) — a
frontend-only specification. Replit produced a single-file, high-fidelity demo
(`artifacts/zari/src/App.tsx`) with inline mock data, plus ~935 lines of
hand-written CSS. There was no backend, no database, and no service layer.

**Then the backend, database and AI service were built** (August 2026) against
that spec: `backend/` (Node + Express + Prisma), `ai-service/` (Python +
FastAPI), a 46-table Postgres schema, Dockerfiles, and a Render blueprint.

**Then the frontend was wired to the API**, with the original mock data kept as
a fallback so no screen can ever be empty or stuck loading.

**Then it was deployed**, which is where most of the interesting knowledge in
this file came from.

## Decisions that would look arbitrary without the reason

**Money is integer paise everywhere.** ₹8,240 is `824000`. Floats and money do
not mix, and `splitEscrow()` guarantees advance + balance equals the total
exactly, with the rounding remainder landing in the balance.

**Design versions are immutable.** Every edit inserts a new `DesignVersion`
carrying a `parentVersionId`. That pointer is the entire mechanism behind
branching, undo, and compare. Nothing is ever updated in place.

**Escrow is a ledger, not a payment-provider feature.** Money is captured to the
Zari account and written as `LedgerEntry(CREDIT, HELD)`. `releaseEscrow()` is
called from exactly one place — the QC pass path. There is deliberately no admin
shortcut to pay a designer early, because that shortcut is the thing customers
are trusting does not exist.

**The AI service is a separate deployment.** It is the only slow, expensive,
provider-dependent part. Keeping it separate means it can be scaled, rate
limited, rolled back, or swapped without touching the API, and it holds no user
data at all.

**The AI service never invents prices.** The backend loads active `CostRule`
rows and passes them in; the prompt states those are the only rates permitted.
This is why ops owns `/ops/cost-rules` — it is the pricing knowledge base, not a
settings page.

**Model output is parsed tolerantly, user input strictly.** The spec schema
coerces: it truncates at word boundaries, caps arrays, and normalises casing and
synonyms. A model that answers "Medium" instead of "MEDIUM" has still done its
job, and rejecting it would turn a good generation into a 500 that loses the
customer's work.

**The frontend always has data.** `useApiData` returns live data when the API
answers and the bundled demo set when it does not — including when the API
returns an empty list, since a fresh environment showing nothing is a worse
first impression than sample content. It also reports `isLive`, and every screen
renders a "Sample data" chip when false. Showing demo content without saying so
would break the one promise the product is built on.

## Production failures, in the order they were hit

Every one of these cost real time. They are recorded so they cost nobody else any.

### 1. `P1001: Can't reach database server`
Supabase's **direct** connection host (`db.<ref>.supabase.co:5432`) is IPv6-only
on new projects. Render's egress is IPv4. Migrations therefore failed on deploy
while working perfectly from a laptop that had IPv6 — the worst kind of bug.
**Fix:** `DIRECT_URL` must be the **session pooler**
(`aws-0-<region>.pooler.supabase.com:5432`). Both pooler URLs use the username
`postgres.<project-ref>`, not `postgres`.

### 2. `P1013: The provided database string is invalid`
A `.env` file carries quotes and dotenv strips them, so the quoted form was
pasted into Render's env var UI where it stayed literal. Prisma saw a scheme of
`"postgresql` and reported a malformed URL, which reads like a bad host.
**Fix:** paste values without quotes. `docker-entrypoint.sh` now strips
surrounding quotes and fails with a message naming the real problem.

### 3. `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` on the Static Site
pnpm 10 reads `overrides` from `pnpm-workspace.yaml` and records them in the
lockfile; pnpm 9 ignores them entirely. The lockfile was generated by 9, so every
pnpm 10 `--frozen-lockfile` install failed — which is what Render runs — while
the same install passed locally on 9.
**Fix:** `packageManager: "pnpm@10.34.5"` pinned in the root package.json, and
the lockfile regenerated with that version.

### 4. `EROFS: read-only file system, unlink '/usr/bin/pnpm'`
The Static Site build command started with `corepack enable`. Render mounts
`/usr/bin/pnpm` read-only.
**Fix:** drop it. Render runs its own `pnpm install` before the build command
and honours `packageManager`, so the build command only has to build.

### 5. `OpenAI connection error: Connection error.`
`OPENAI_BASE_URL=""` was copied from `.env.example` into Render, where the value
became two literal quote characters — which is truthy in Python, so the client
was constructed with a malformed base URL.
**Fix:** a before-validator in `ai-service/app/config.py` strips surrounding
quotes and whitespace from every string setting, killing this whole class of bug.

### 6. A bare `500 INTERNAL` after the model had already succeeded
Two separate causes, found in sequence:
- **Prisma's interactive transaction timeout is 5 seconds.** `generate` wrapped
  all four concepts in one transaction — ~24 sequential round trips against a
  pooled database in another region. It threw `P2028`, which no branch of the
  error handler recognised. **Fix:** one transaction per concept with a 20s
  timeout, and a failure now saves the others rather than losing the batch.
- **Three call sites used the global `prisma` client inside an open `tx`.**
  `DATABASE_URL` has `connection_limit=1`, so the open transaction held the only
  connection and the inner query waited for a connection that could not be
  released — a self-deadlock. **Fix:** `designers.createProfile` resolves its
  slug first; `orders.markDelivered` and `orders.submitFitFeedback` recompute the
  quality score after the transaction closes.

### 7. `403 FORBIDDEN` returning every fifteen minutes
The worst one, because it looked like the guest quota working correctly.
`attachIdentity` swallowed an invalid bearer token and let the request continue
as a guest. So a signed-in customer whose 15-minute access token expired was
demoted to a guest, refused by the guest quota, and handed a **403** — which the
client does not refresh on, because only a **401** means "your token is stale".
Signing in again changed nothing.
**Fix:** a supplied token is a claim of identity, so an invalid one is flagged
and every guard turns it into a 401. The client already refreshes and replays on
401, which closes the loop.

### 8. The AI service blocking its own event loop
`structured_call` used the **synchronous** OpenAI client inside `async def`
routes. With one uvicorn worker, every generation blocked the event loop for its
full 30-60 seconds — the service answered nothing else in that window, including
`/health`, which Render reads as a dead container.
**Fix:** `AsyncOpenAI`, awaited at every call site. Confirmed by `/health/ready`
going from timing out to instant.

### 9. Image generation running the clock out
With `IMAGE_PROVIDER=openai`, a generation waited on four renders with no
ceiling and exceeded the backend's timeout — losing specs and pricing the model
had already produced, because a picture was slow.
**Fix:** renders run under a fixed 60s budget. Whatever is unfinished is dropped
and the concepts return without imagery, which is the correct trade.

## Bugs that were in the frontend from the very first build

- **`tone` was never read.** The prop was passed everywhere — designs, concepts,
  portfolio — but no CSS rule consumed it, so every garment illustration rendered
  the same pink and four distinct concepts looked like one repeated four times.
- **The studio canvas ignored the render.** The listing passed cover images to
  `GarmentArt`; the studio — the screen built around looking at the garment —
  did not.
- **`GUEST_FREE_GENERATIONS` counted designs, not generations.** One generation
  creates four concepts, so any value below 4 allowed exactly one generation and
  raising it changed nothing.

## Backend warts worth knowing before you touch these paths

Found while building the ops console against the real routes.

- **`POST /api/qc/start` takes an `orderId`, not a check id, and always opens a
  NEW round** (`round = last + 1`). Starting a `NOT_STARTED` queue row does not
  transition it — it leaves it orphaned and inserts round N+1.
- **`GET /api/qc/queue` omits the check's `items`.** The five criteria rows only
  come back from `/start`, `/photos` or `/decide`, so the queue screen
  synthesises them client-side.
- **A QC pass leaves the order at `QC_PENDING`.** There is no `QC_PASSED` in
  `OrderStatus`, and the pass lives on the QualityCheck row — which is what
  `markShipped()` gates on. The behaviour is correct; the status name is
  misleading. Do not "fix" this by setting `SHIPPED` on pass: the garment has
  cleared inspection but has not been dispatched, and claiming otherwise would
  be a real bug. The clean fix is a `QC_PASSED` enum value and a migration.
- **`DELETE /api/ops/cost-rules/:id` does not delete** — it sets
  `isActive: false`. And `GET` returns inactive rows too, so a client has to
  separate in-use from retired itself. `POST` upserts on
  `(component, key, region)`, so re-posting a retired key revives it.
- **`RESOLVED_CUSTOMER` cancels the order; `RESOLVED_DESIGNER` and
  `RESOLVED_SPLIT` complete it.** Not inferable from the enum names.
- **Verification posts to the designer PROFILE id**
  (`POST /ops/designers/:designerId/verify`), while `GET /ops/designers`
  returns `DesignerVerification` rows whose `id` is a different value.

## Still open

- `App.tsx` still holds every page in one file. The data layer beneath it
  (`lib/`, `services/`, `hooks/`) is done; the extraction is not.
- Designer and ops screens: see the log below for current status.
- Real version-tree UI (branch, compare, jump) and the full-screen budget
  optimizer with per-substitution toggles. Both are fully supported by the API.
- `maxWait` is 2s against a one-connection pool, so two concurrent requests can
  still produce `P2028`. The error handler maps it to a retryable 503, but the
  real fix is raising `connection_limit` once there is more than one user.
- Messaging is REST-polled; there are no websockets.
- No courier integration — ship and deliver are manual ops actions.

## Session log

Newest last. Each entry: what changed, and anything a future session must know.

### 2026-08-09 — Backend, database and AI service built
Node + Express + Prisma API with auth (phone OTP, email/password, guest mode
with claim-on-signup), immutable design versions, budget optimizer, marketplace
matching and bidding, orders, ledger-backed escrow, Razorpay payments and
webhooks, QC gating the escrow release, fit window, messaging, designer
dashboard/copilot/earnings, ops console, signed uploads. 46-table schema with a
baseline migration. Python AI service on Claude, then migrated to OpenAI.
Dockerfiles, docker-compose, Render blueprint, documented `.env.example` files.

### 2026-08-09 — AI service moved from Anthropic to OpenAI
Chat completions with strict Structured Outputs replacing `output_config`, and
`reasoning_effort` replacing adaptive thinking. Imagery moved to `gpt-image-2`
behind the same key. GPT Image returns base64 rather than a hosted URL, so the
AI service hands the bytes to the backend, which uploads them to Supabase
Storage — storage ownership stays in one place.

### 2026-08-10 — Frontend wired to the API
Typed client with bearer + guest token handling, envelope unwrapping, and
refresh-and-replay on 401. Service modules normalise API rows into view types.
`useApiData` gives every screen live-or-demo data plus an `isLive` flag.

### 2026-08-10 — Deployed, and the nine failures above were found and fixed
See "Production failures". Live at that point: designs, designer directory,
orders, auth, generation with real specs and pricing, and real `gpt-image-2`
renders reaching Supabase and appearing in the UI.

### 2026-08-10 — Designer and ops screens built, and a money bug found
Five designer pages (`/designer`, `/bids`, `/copilot`, `/earnings`, `/quality`)
and five ops pages (`/ops`, `/qc`, `/designers`, `/disputes`, `/cost-rules`),
each with its own shell, service and hooks. Both sections are `React.lazy`
split — a customer never opens them, so they are not in the main bundle.

Building the ops console against the real routes surfaced the warts listed
above, and one genuine money bug: **dispute resolution refunded before it
recorded the resolution**, so a Razorpay refund could succeed while the write
that explains it failed — money gone with nothing saying why, and the dispute
still open for someone to resolve a second time. The order is now reversed and
the resolution is idempotent; a failed refund returns `refundError` and leaves a
recorded resolution for ops to retry.

### 2026-08-10 — Version tree, real budget optimizer, and an honesty audit
The two features the brief calls distinctive are built: a real version tree
(branching off `parentVersionId`, undo/redo, jump, compare with a price delta)
and the full budget optimizer (per-substitution toggles, server-computed live
totals, INFEASIBLE as a first-class state). Both replaced hardcoded panels in
the studio that showed invented plans beside a live estimate.

A read-only audit of the frontend then found a set of honesty defects worth
recording, because each is the same mistake in a different place — showing
something invented as though it were measured:

- **The "Sample data" chip never appeared in the demo build.** `DemoNote` bailed
  out when `VITE_API_URL` was unset, which is exactly the deployment where every
  screen is sample content. It showed only in the narrow case where the URL was
  set but the server was down.
- **Fabricated per-designer statistics.** The marketplace card computed a "fit
  success" percentage from array position, and the profile's "Quality Score,
  made legible" panel showed three constants as that studio's measured
  breakdown. Both now render from `GET /api/marketplace/scoring`, the same
  endpoint the marketplace ranks with.
- **The order page's entire money panel was hardcoded** — a fixed ₹6,400, a
  fixed 40/60 split and a fixed timeline, rendered on top of a live order's
  title and designer, so a real order showed someone else's price. The endpoint
  that supplies all of it was already written and had no caller.
- **The concepts screen invented a fallback price** for a concept with no
  estimate. It now says "Not priced yet".
- **`tone` had recurred** on `.maker-art` and `.journey-art` — attributes no CSS
  rule reads.

Also fixed from the ops build: a QC pass on an order with nothing held in escrow
recorded the pass, notified both parties, and then returned a 409 to the
reviewer. Nothing held is a legitimate state, not a failure — `releaseEscrow`
now returns null instead of throwing.

### 2026-08-10 — Landing page rebuilt around the product's actual argument
Added the five-step journey strip, an itemised estimate section, a budget
optimizer section naming what each substitution costs, and an escrow strip
stating trust as mechanics. Hero now carries a real estimate. Designer cards use
real portfolio work where a studio has uploaded it. Garment tone variants
implemented for the first time.
